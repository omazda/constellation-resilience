# Параметры, влияющие на результат

Инвентаризация всего, что читается из сценария или выбирается нами и меняет итоговые числа.
Все значения ниже получены прогоном на `Данные/*.json` через официальный `geometry.py`,
воспроизводятся командами из раздела «Как перепроверить».

## 1. Параметры среды (`environment`) — задаются файлом, менять нельзя

| Поле | В наборе | Границы `validate()` | Влияние |
|---|---|---|---|
| `altitude_km` | 550 | 200…1200 | радиус орбиты и угловая скорость `n = √(μ/r³)` |
| `inclination_deg` | 87 | 0 < i ≤ 180 | широтный охват; 87° — почти полярная, север покрыт |
| `earth_angle0_deg` | 12 | конечное | начальный поворот Земли; **потеря даёт тихую ошибку** |
| `horizon_s` | 86 400 | ≤ 172 800, кратно шагу | длина расчёта |
| `step_s` | 120 | целое > 0 | размер отсчёта; **влияет на метрики** |
| `min_elevation_deg` | 10 | 0 ≤ x < 90 | **самый чувствительный параметр модели** |
| `isl_range_km` | 3000 / 2000 | 0 < x ≤ 10 000 | наличие межспутниковой сети |
| `target_availability` | 0.9 | 0…1 | планка, относительно которой делается вывод |

### Чувствительность к `min_elevation_deg` (01, остальное неизменно)

| Порог | C65 | C70 | C72 |
|---|---|---|---|
| 5° | 100.00 % | 100.00 % | 100.00 % |
| **10° (в файле)** | **96.67 %** | **98.75 %** | **98.89 %** |
| 15° | 77.36 % | 89.31 % | 90.42 % |
| 20° | 35.69 % | 50.56 % | 55.00 % |

Пять градусов порога стоят 20 процентных пунктов доступности. Отсюда прямое следствие: **снижать
порог, чтобы «дотянуть до 90 %», нельзя** — ТЗ фиксирует, что высота, дальность и угол возвышения
сохраняются при сопоставлении вариантов, а исследование других значений оформляется отдельным
запуском с явным отображением новых условий. Иначе сравнение вариантов теряет смысл.

### Чувствительность к `step_s` (01)

| Шаг | C65 | макс. перерыв C70 |
|---|---|---|
| 60 с | 97.01 % | 2 мин |
| **120 с (в файле)** | **96.67 %** | **2 мин** |
| 240 с | 96.67 % | 4 мин |
| 480 с | 96.67 % | 8 мин |

Метрика — доля отсчётов, а не интеграл по времени, поэтому она зависит от сетки, а максимальный
перерыв квантуется шагом. Поэтому варианты сравниваются **только на одинаковой сетке**, и шаг
показывается рядом с числами.

### `earth_angle0_deg`

Обнуление 12° меняет C65 с 96.67 % на 96.39 %, C72 с 98.89 % на 98.75 %. Ошибка маленькая и оттого
опасная: числа остаются правдоподобными, расхождение с эталоном списывается на «другой алгоритм».

## 2. Параметры конфигурации (`design`) — этим пользователь и управляет

| Поле | Что делает | Границы |
|---|---|---|
| `launch_stage` | сколько очередей запущено | **целое, ровно 1, 2 или 3** |
| `planes[].raan_deg` | ориентация плоскости | `0 ≤ x < 360`, 360 недопустимо |
| `planes[].phase_deg` | сдвиг аппаратов вдоль орбиты | `0 ≤ x < 360` |
| `satellites[].slot_deg` | положение в плоскости | только конечное, диапазон не ограничен |
| `satellites[].launch_batch` | очередь аппарата | 1, 2 или 3 |

Формы UI обязаны уважать эти границы: слайдер RAAN до 360 включительно или `launch_stage` как
дробное значение роняют валидацию на стороне сервера.

### Подбор RAAN — сколько он даёт (04, ISL 2000 км, цель 90 %)

| RAAN плоскостей | C65 | C70 | C72 |
|---|---|---|---|
| 0/30/60 | 61.25 % | 63.61 % | 67.08 % |
| 0/40/80 | 73.06 % | 67.78 % | 73.06 % |
| **0/50/100 — лучшее найденное** | **78.61 %** | **71.94 %** | 69.86 % |
| 0/60/120 (в файле) | 77.50 % | 62.22 % | 65.14 % |
| 0/90/180 | 64.31 % | 55.28 % | 51.39 % |
| 0/120/240 | 72.22 % | 64.17 % | 58.06 % |

Перебор ориентации даёт C70 почти +10 п.п., но **90 % не достигается ни при какой ориентации**:
при ISL 2000 км упирается не в геометрию плоскостей, а в разрыв межспутниковой сети (см. ниже).
Это и есть честный вывод для отчёта — с указанием, что именно нужно менять вместо RAAN.

## 3. Механика сценария 04: почему падает именно доступность, а не покрытие

Радиус орбиты `r = 6371 + 550 = 6921` км, в плоскости 16 аппаратов, шаг по орбите 22.5°.
Хорда между соседями по плоскости:

```
2 · 6921 · sin(11.25°) = 2700 км
```

При `isl_range_km = 3000` соседи связаны, при 2000 — нет. Замер по рёбрам подтверждает:

| Сценарий | межспутниковых рёбер | внутри плоскости | между плоскостями |
|---|---|---|---|
| 01 (ISL 3000) | 5338 | 3456 (65 %) | 1882 |
| 04 (ISL 2000) | 1002 | **0 (0 %)** | 1002 |

Кольцо каждой плоскости рвётся целиком, остаются только редкие межплоскостные контакты. Видимость
со спутника при этом не меняется (97.78 / 99.86 / 100 %) — падает сквозная достижимость. Это
и есть тезис кейса «видимость ≠ маршрут», выраженный числом.

Чтобы восстановить связность внутри плоскости при 2000 км, нужно **не менее 22 аппаратов в
плоскости** (шаг 16.4°, хорда 1970 км) вместо 16 — готовая проектная рекомендация.

## 4. Правила расчёта, которые легко нарушить незаметно

- **Сетка.** Отсчёты `0 … horizon_s − step_s`, правый конец не включается. При 86 400/120 это 720.
- **Активность.** `launch_batch ≤ launch_stage` и момент вне `failures`. Интервалы — `[start, end)`,
  пересекающиеся объединяются по смыслу недоступности.
- **Отказавший аппарат сохраняет положение** и исключается только из связей: на схеме он остаётся
  на орбите, но серым.
- **Неравенства строгие ровно там, где в ТЗ**: ISL при `d < isl_range_km`, отсутствие пересечения
  с Землёй при `closest > R`, наземный контакт при `elevation ≥ min_elevation_deg`. За сутки
  находится 18 пар в пределах ±1 км от порога ISL и 198 пар в ±1 км от касания Земли — границы
  реально достигаются, «примерно» здесь не работает.
- **Клиентские пункты не ретранслируют.** В рёбрах снимка есть линии «клиент ↔ спутник», поэтому
  обычный обход графа построит путь через второй клиентский пункт. Цена ошибки замерена:

  | Сценарий | правильно | наивный обход | завышение |
  |---|---|---|---|
  | 01 | 96.67 / 98.75 / 98.89 % | то же | 0 |
  | 03 | 79.31 / 80.83 / 82.50 % | 79.31 / 80.97 / 82.64 % | +0.14 п.п. |
  | **04** | 77.50 / 62.22 / 65.14 % | 83.61 / 73.19 / 75.28 % | **до +11 п.п.** |

  На полной группировке ошибка не видна вообще и вылезает только на деградированной сети — то есть
  ровно там, где делаются выводы.
- **Шлюзов может быть несколько**, и у каждого свои `gateway_outages`; маршрут строится до любого
  доступного. В наборе шлюз один, но проверять будут чужим файлом.
- **Цензурированные перерывы.** Перерыв, упирающийся в начало или конец горизонта, усечён и
  учитывается отдельно. Факт: в 02 на конце горизонта висят перерывы 106 мин (C65), 164 мин (C70),
  2 мин (C72) — они короче настоящих.
- **`snapshot()['elevation_deg']` содержит только активные аппараты** — не строить по нему список
  всей группировки.
- **Число переходов** = число рёбер, включая обе наземные линии, минимум 2. Нет пути — значения нет.

## 5. Параметры, которые выбираем мы (их надо обосновать в отчёте)

### Стратегия маршрутизации

Доступность и максимальный перерыв **не зависят** от алгоритма — это достижимость в графе.
Отличаются длина маршрута, число переходов и стабильность картинки (01, полные сутки):

| Стратегия | доступность | смен пути C72 | переходы, медиана | длина, медиана C72 | максимум |
|---|---|---|---|---|---|
| BFS по числу переходов | 96.67 / 98.75 / 98.89 % | 599 из 712 (84 %) | 2–3 | 5007 км | 7792 км |
| BFS + удержание валидного пути | то же | 450 из 712 (63 %) | 2–3 | 5287 км | 8868 км |
| Дейкстра по километрам | то же | 547 из 712 (77 %) | 2–3 | 4602 км | 7621 км |

Выводы для защиты: BFS даёт минимум переходов, но маршруты до 10 000 км; Дейкстра короче на
8 % по медиане при той же доступности; удержание предыдущего маршрута, пока он валиден, снимает
пятую часть перестроений и делает анимацию читаемой. Смена пути в половине–трёх четвертях
отсчётов — это свойство LEO на шаге 120 с, а не дефект: топология действительно меняется.

### Прочее

- Порядок обхода соседей влияет на то, какой из равноценных путей выбран: фиксируй сортировку,
  иначе одинаковые запуски дадут разные `path` в выгрузке.
- Расчёт ведём в float64; в float32 переводим только для передачи на фронтенд.
- Точка отсчёта времени — секунды от начала расчёта, не UTC.

## 6. Требования, которые легко забыть

- **Выгрузка изменённого сценария** в формате `cosmo-A-1.0` и его повторная загрузка — отдельный
  экспорт, не тот же, что выгрузка результата `cosmo-A-result-1.0`.
- **Сброс изменений и новый запуск** для повторного эксперимента.
- **Причина отсутствия маршрута** в четырёх вариантах: нет видимого спутника, разрыв межспутниковой
  сети, нет контакта со шлюзом, шлюз недоступен.
- **Подписи на схеме** должны давать определить аппарат и его состояние.
- **Диаграмма доступности** — интервалы связи и перерывы по каждому пункту, не одна сводная цифра.
- **В сравнении** видны изменённые параметры, итоговые показатели и различия между ними.
- `sunlight()` в `geometry.py` считает освещённость и тень Земли. В требованиях её нет — это
  готовый задел для дополнительного функционала, но не за счёт обязательной части.

## Как перепроверить

```bash
python3 tools/golden.py                          # эталонные метрики по всем сценариям
python3 tools/golden.py --result out.json        # проверка выгрузки сервиса
```

Числа чувствительности получены подстановкой значений в `environment`/`design` загруженного
сценария и повторным прогоном того же расчёта достижимости.
