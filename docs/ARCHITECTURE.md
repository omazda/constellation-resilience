# Архитектура сервиса

![Архитектура](graph.svg)

## Из чего собран сервис

Один процесс, один порт (8000), один Docker-образ (`Dockerfile`, см. корень репозитория):

- **`backend/core/`** — расчётное ядро. Чистые функции над сценарием (`dict`) и числами, ни одного
  импорта из веб-слоя (`app/`) — граница проверяется буквально: `core/` запускается и тестируется
  без FastAPI (`python3 backend/core/metrics.py`, `pytest backend/tests`). Здесь же лежит
  `geometry.py` — побайтовая копия официального «Расчетный модуль/geometry.py» из комплекта задачи
  (формулы орбит и видимости не переписываются, копия нужна только потому, что Docker-образ
  собирается исключительно из `backend/`).
- **`backend/app/`** — веб-слой. FastAPI-приложение с единственным расчётным каналом `/ws`
  (`ws.py`, контракт — `docs/PROTOCOL.md`) плюс `/health` для healthcheck и раздача статики
  фронтенда/сэмплов сценариев. Слой тонкий: разбирает конверт, проверяет форму `payload`, вызывает
  `core/` и раскладывает результат в проводной формат — ни одной формулы или алгоритма
  маршрутизации здесь нет.
- **`frontend/`** — Nuxt 4 SPA (`ssr:false`) на Nuxt UI v4, глобус — `globe.gl`. Собирается
  статически (`nuxt generate` → `.output/public`) и раздаётся тем же FastAPI-процессом из
  `backend/static/` — сервис доступен жюри по одной ссылке без отдельного веб-сервера для фронтенда.
- **`tools/golden.py`** — независимый эталон. Не импортирует `core/` вовсе: свой обход
  `geometry.snapshot()`, своя BFS-достижимость (с тем же правилом «клиентский пункт не
  ретранслирует»), сверяет и посчитанные ядром метрики, и итоговую выгрузку сервиса
  (`--result <файл>`). Расхождение с ним — ошибка модели в `core/`, а не другой, тоже верный, подход
  (это прямо обосновано докстрингом самого `tools/golden.py`).

## Граница ядро/веб-слой и куда идут данные

1. **Загрузка.** Браузер отправляет сырой JSON `cosmo-A-1.0` сообщением `scenario.load`. Веб-слой
   зовёт `core.scenario.load_scenario()` — валидация (границы `geometry.validate()` плюс требования
   «Описания данных»: конечные числа, уникальные ID, разрешимые ссылки, `horizon_s % step_s == 0`)
   поднимает `ScenarioError(field, message)` с именем проблемного поля, а не падает `KeyError`/
   трейсбеком. Успешный сценарий получает `variant_id = core.scenario.scenario_hash(...)` и
   сохраняется в памяти процесса (`app/ws.py::_Store`).
2. **Правка.** `scenario.patch` не изменяет существующий вариант — `core.scenario.patch_scenario()`
   возвращает новый сценарий, у него новый `variant_id`. Сценарии в сервисе иммутабельны: «сохранить
   вариант и вернуться к нему» (DoD п.1) — это просто список запомненных `variant_id` на клиенте,
   бэкенду отдельное хранилище вариантов не нужно.
3. **Расчёт.** `compute` — единственный источник истины: один вызов `core.metrics.compute()` на весь
   горизонт (720 отсчётов на эталонных данных), тот же самый, что сверяется с `tools/golden.py`
   (`backend/tests/test_golden.py`). Дополнительный проход по `core.network.snapshot()` в
   `_compute_pipeline` нужен только за тем, чего `compute()` не отдаёт по построению (он компактен —
   доли/перерывы/маршруты, а не сырые координаты и рёбра): позициями спутников и рёбрами сети для
   отрисовки, плюс причиной отсутствия пути там, где маршрута нет (`core.routing.no_route_reason`,
   тоже не переизобретается). Выполняется в `asyncio.to_thread`, результат кешируется по
   `(variant_id, strategy)` и упаковывается в манифест + один бинарный фрейм (`docs/PROTOCOL.md`).
4. **Точечный доступ.** `snapshot` — тот же `core.network.snapshot()`/`core.routing.find_route()` на
   один момент `t_s`, без сохранения в кеш; берёт маршрут из уже готового `compute`, если он есть.
5. **Сравнение.** `compare` досчитывает (или берёт из кеша) оба варианта и сравнивает
   `client_metrics` из их манифестов — сравнение не пересчитывает геометрию заново, только читает
   то, что уже посчитал `compute`.
6. **Выгрузка.** `export` с `kind:"result"` отдаёт `{schema_version:"cosmo-A-result-1.0",
   effective_scenario, routes}` — `routes` берётся из уже посчитанного `compute()["routes"]`
   (`core.scenario.export_scenario` не пересчитывает и не округляет: `export_scenario(load_scenario(raw)) ==
   raw`). `kind:"scenario"` отдаёт только изменённый `cosmo-A-1.0` — для повторной загрузки после
   правок (DoD «выгрузка изменённого сценария и повторная загрузка» — это два разных документа, не
   один и тот же).

Схема этого потока — `docs/graph.svg` выше.

## Почему кеш в памяти процесса, а не файл/БД

`backend/app/ws.py::_Store` — простой словарь `dict` в памяти. Сознательное упрощение, а не
недосмотр: контракту (`.claude/rules/protocol.md`) достаточно, чтобы `attach` после обрыва
**соединения** отдавал готовый результат без пересчёта — переживание перезапуска **процесса**
контрактом не требуется. Хранилище вариантов и БД сохранённых конфигураций поверх (SQLite/JSON-файлы
на диске, DoD п.1 «сохранение варианта») по стеку задачи (см. корневой `CLAUDE.md`) допустимы, но не
обязательны технически — `variant_id` уже детерминирован по содержимому сценария
(`scenario_hash`), так что список сохранённых вариантов может жить целиком на клиенте (`localStorage`
или состояние страницы), обращаясь к тому же бэкенду за пересчётом по `variant_id`.

## Формат бинарного фрейма — почему не JSON

Позиции 48 спутников на 720 отсчётах как JSON-числа — заметно больше по объёму и заметно медленнее
парсится в браузере, чем типизированный массив поверх `ArrayBuffer`. Формат подробно описан в
`docs/PROTOCOL.md` («Бинарный фрейм»): плоский буфер с выровненными по 4 байта секциями, офсеты и
формы — в JSON-манифесте (`payload.layout`), так что порядок секций в буфере не обязан быть
самоописывающимся. Итог на `01_full_constellation.json` — вариант целиком укладывается заметно
меньше мегабайта, и временная шкала на фронтенде скрабится без единого дополнительного запроса к
серверу (`.claude/rules/protocol.md`).

## Тестовая граница

- `backend/tests/test_golden.py` — сверяет `core/` с эталоном по всем четырём сценариям `Данные/*.json`
  ДВАЖДЫ независимыми источниками: со статической таблицей `CLAUDE.md`/`docs/PARAMETERS.md` (защита
  от регрессии) и живым запуском `tools/golden.py::metrics()` на тех же файлах (ловит расхождение,
  даже если входные данные когда-нибудь поменяются). Расхождение с любым из двух — ошибка модели.
- `backend/tests/test_ws.py` — весь контракт `/ws` через `TestClient` FastAPI: все семь типов
  сообщений, все семь кодов ошибок, побитовое совпадение бинарного пакета с `compute`-манифестом,
  кеш по `scenario_hash`, `attach` без пересчёта и после переподключения, устойчивость к мусору на
  проводе (не-JSON, бинарный фрейм от клиента, неизвестный `type`).
- Команда — `cd backend && python3 -m pytest -q` (README, раздел «Тесты»); 73 теста, независимо от
  файла сценария на входе (никаких зашитых `C65`/`G_MUR` в самих проверках — только в таблице
  эталонных чисел, которая явно привязана к комплекту `Данные/`).

## Развёртывание

`Dockerfile` — две стадии (шаблон `.claude/rules/docs.md`): `node:22-alpine` собирает
`frontend/` командой `nuxt generate` (`ssr:false` → статический `.output/public`, серверный рендер
не нужен и не проверяется критериями), `python:3.12-slim` ставит зависимости `backend/`, копирует
`backend/` целиком (включая `core/` с эталонной `geometry.py`), забирает собранную статику фронтенда
в `./static` и сэмплы `Данные/` в `./samples`. Процесс — `uvicorn app.main:app`, один порт 8000,
`docker-compose.yml` поднимает его одной командой. Подробности — README, раздел «Запуск».
