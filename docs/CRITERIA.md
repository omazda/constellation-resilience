# Соответствие критериям оценки

Таблица для проверяющего: что закрывает каждый критерий, где это лежит и **как убедиться самому**.
Каждая строка проверяется либо командой, либо кликом в интерфейсе — ни один пункт не требует
верить на слово.

Сервис: **https://braining.space**. Локально: `docker compose up --build`, затем `http://localhost:8000`.

---

## Отраслевые эксперты — 50 баллов

### 1. Проектирование и сравнение конфигураций — 15

| Требование критерия | Чем закрыто | Как проверить |
|---|---|---|
| выбирать этап развёртывания | `launch_stage` 1/2/3 в форме | вкладка «Настройка» → очередь запуска → пересчёт |
| изменять параметры плоскостей | `raan_deg`, `phase_deg` по каждой плоскости | там же, поля с границами 0…359.999 |
| сравнивать варианты | сообщение `compare`, вкладка «Сравнение» | сохранить вариант, изменить, сравнить |
| результат помогает выбрать конфигурацию | вывод над таблицей сравнения: какой вариант предпочесть и при каком условии | виден сразу после расчёта сравнения |

Дополнительно: сравнение **отказывается молча сопоставлять несопоставимое** — если у вариантов
различаются `altitude_km`, `isl_range_km`, `min_elevation_deg` или сетка, выводится предупреждение,
что числа посчитаны честно, но вывод «B лучше A» по ним делать нельзя (`docs/PARAMETERS.md §1`).

### 3. Обоснованность рекомендаций — 10

`docs/REPORT.md` — инженерный отчёт: сравнение конфигураций, анализ отказов, рекомендация с
условиями достижения 90 % и ограничениями. Все числа воспроизводятся командами из
`docs/PARAMETERS.md` и `docs/EXTENSIONS.md`.

Ключевые выводы, каждый с числом: цель достижима только на полной группировке при ISL 3000 км;
при 2000 км рвутся все внутриплоскостные связи (0 из 3456), потому что хорда между соседями
2700 км; узкое место проекта — единственный шлюз, а не группировка.

## Технические эксперты — 50 баллов

### 6. Корректность расчётов — 15

```bash
python3 tools/golden.py                    # сверка с эталоном по всем четырём сценариям
python3 -m pytest backend/tests -q         # 73 теста
```

`tools/golden.py` считает независимо от сервиса, напрямую через официальный
`Расчетный модуль/geometry.py`. Доступность и максимальный перерыв — это достижимость в графе,
она не зависит от алгоритма маршрутизации, поэтому совпадение чисел — доказательство, а не
совпадение подходов.

| сценарий | C65 | C70 | C72 |
|---|---|---|---|
| 01 полная группировка | 96.67 % | 98.75 % | 98.89 % |
| 02 первая очередь | 27.22 % | 15.83 % | 12.64 % |
| 03 отказ 10 аппаратов | 79.31 % | 80.83 % | 82.50 % |
| 04 ISL 2000 км | 77.50 % | 62.22 % | 65.14 % |

Проверка выгрузки сервиса: `python3 tools/golden.py --result <файл>` — формат, полнота пар
`(t_s, client_id)`, физическая допустимость каждого ребра маршрута.

### 7. Алгоритмы маршрутизации — 15

| Требование | Чем закрыто | Как проверить |
|---|---|---|
| поиск допустимых маршрутов | BFS по числу переходов и Дейкстра по километрам | переключатель стратегии в шапке |
| обновление маршрутов | пересчёт на каждом отсчёте, удержание валидного пути | перемотка полосы суток |
| обработка разрывов и отказов | четыре причины отсутствия пути | задать отказ аппарата из текущего маршрута |
| обоснованность подхода | обе стратегии дают **одинаковую доступность** и разную длину маршрута | переключить стратегию: проценты не меняются, переходы и длина меняются |

Это и есть демонстрация, что доступность — свойство сети, а не алгоритма. Замеры трёх стратегий
(включая удержание маршрута) — `docs/PARAMETERS.md §5`.

Ограничение, соблюдаемое строго: **клиентские пункты не ретранслируют**. Наивный обход графа
завышает доступность до +11 п.п. на `04_link_range` — замер там же.

### 8. Работа с входными данными — 10

| Требование | Как проверить |
|---|---|
| загрузка дополнительного сценария того же формата | перетащить свой файл `cosmo-A-1.0` в сайдбар |
| применение изменений из интерфейса | «Настройка» → правка → новый `variant_id` |
| корректный повторный расчёт | числа меняются, сверка с `golden.py` сохраняется |
| сохранение параметров | вариант сохраняется и доступен в сравнении |
| выгрузка результата | кнопка «Результат» → `cosmo-A-result-1.0` |
| выгрузка изменённого сценария | кнопка «Сценарий» → `cosmo-A-1.0`, загружается обратно |
| понятные сообщения об ошибках | подсунуть битый файл: ответ называет поле, а не отдаёт трейсбек |

Никакого хардкода идентификаторов: сервис проверялся на синтетическом сценарии с другими ID
плоскостей, аппаратов и пунктов.

### 9. Качество кода — 5

- `backend/core/` — расчётное ядро, **ни одного импорта из веб-слоя**; запускается без FastAPI.
- `backend/app/` — только транспорт: принимает конверт, зовёт ядро, отдаёт ответ.
- `backend/core/geometry.py` — побайтовая копия официального модуля, формулы не трогались.
- 73 теста, включая сверку с независимой реализацией в `tools/golden.py`.

```bash
diff "Расчетный модуль/geometry.py" backend/core/geometry.py   # должно быть пусто
grep -rn "from app\|import app" backend/core/                   # должно быть пусто
```

### 10. Документация и запуск — 5

- `docker compose up --build` — один образ из двух стадий, порт 8000.
- `README.md` — запуск первой командой, демо-сценарий, формат данных, тесты, ограничения.
- `docs/PROTOCOL.md` — все восемь сообщений `/ws` с примерами живых ответов.
- `docs/ARCHITECTURE.md`, `docs/REPORT.md`, `CHANGELOG.md`.
- Образ поднимается на машине без локальных Python и Node; шрифты, текстуры и география лежат
  внутри образа, интернет не нужен.

## Что намеренно не делалось

- **Презентация** — см. критерий 5.
- **Автоматический подбор конфигурации** — необязательный пункт ТЗ. Перебор ориентации плоскостей
  выполнен исследованием (`docs/PARAMETERS.md §2`), в сервисе его нет.
- **Модель радиоканала** — ТЗ прямо разрешает ограничиться геометрией; пропускная способность и
  очереди не считаются, о чём сказано в `README.md`.
