# Расширенные параметры и новые постановки

Всё ниже посчитано на `Данные/*.json` через официальный `geometry.py`. Обязательные показатели ТЗ
(доступность, перерывы, переходы) остаются как есть — это надстройка над ними. Контрольная сверка:
колонка «сейчас» в таблицах задержки совпадает с эталоном `tools/golden.py` до сотых.

## 1. Доставляемость с допуском по задержке

**Идея.** Обязательная метрика отвечает на вопрос «есть ли путь прямо сейчас». Но в спутниковой
связи данные могут подождать на борту и уйти следующим контактом. Считается это на временном графе:
узел — пара «аппарат, отсчёт», рёбра — связи в этот момент плюс рёбра ожидания «тот же аппарат,
следующий отсчёт». Ждать разрешено только спутнику: наземный пункт не ретранслирует.

Доля отсчётов, из которых данные доставляются в шлюз с задержкой не более T:

|---|---|---|---|---|---|---|
| 01 полная | C65 | 96.67 % | 97.78 % | 97.78 % | 97.78 % | 97.78 % |
| | C70 | 98.75 % | 99.86 % | 99.86 % | 99.86 % | 99.86 % |
| | C72 | 98.89 % | 100.00 % | 100.00 % | 100.00 % | 100.00 % |
| 03 отказы | C65 | 79.31 % | 82.08 % | 83.19 % | 83.89 % | 84.58 % |
| | C70 | 80.83 % | 85.28 % | 86.94 % | **89.58 %** | 90.28 % |
| | C72 | 82.50 % | 87.22 % | 89.31 % | **92.50 %** | 93.06 % |
| **04 ISL 2000** | C65 | 77.50 % | 81.81 % | 85.97 % | **90.42 %** | 90.42 % |
| | C70 | 62.22 % | 79.72 % | 88.89 % | **95.00 %** | 95.00 % |
| | C72 | 65.14 % | 86.67 % | 96.53 % | **96.53 %** | 96.53 % |
| 02 первая очередь | C65 | 27.22 % | 29.44 % | 30.42 % | 31.25 % | 37.22 % |
| | C70 | 15.83 % | 18.06 % | 19.03 % | 19.86 % | 26.81 % |

**Что это даёт.** Сценарий 04, формально проваливающий цель 90 %, достигает её по всем пунктам при
допустимой задержке 10 минут. Сценарий 03 — почти достигает. А сценарий 02 не спасает никакая
задержка: там пункт часто вообще не видит ни одного аппарата, и проблема в покрытии, а не в
маршрутизации. Это разделение диагнозов — готовый вывод для раздела рекомендаций, и его нельзя
получить из обязательных метрик.

ТЗ это прямо разрешает: «Расчёт пропускной способности, очередей передачи и задержки ожидания
контакта команда может добавить отдельным функционалом».

## 2. Резерв маршрутов: сколько отказов переживёт связь

Число вершинно-непересекающихся маршрутов «пункт → шлюз» (теорема Менгера, поиск максимального
потока при единичной пропускной способности аппаратов). Это ответ на вопрос, которого нет в
обязательных метриках: связь держится на одной нитке или есть запас.

| Сценарий | пункт | нет пути | 1 путь | 2 пути | 3 пути | **резерв ≥ 2** |
|---|---|---|---|---|---|---|
| 01 полная | C65 | 3.33 % | 80.14 % | 15.83 % | 0.69 % | **16.53 %** |
| | C70 | 1.25 % | 68.19 % | 30.42 % | 0.14 % | **30.56 %** |
| | C72 | 1.11 % | 61.67 % | 33.75 % | 3.47 % | **37.22 %** |
| 04 ISL 2000 | C65 | 22.50 % | 71.81 % | 5.00 % | 0.69 % | **5.69 %** |
| | C70 | 37.78 % | 51.11 % | 11.11 % | — | **11.11 %** |
| | C72 | 34.86 % | 61.94 % | 3.19 % | — | **3.19 %** |

**Главный вывод проекта.** Полная группировка выполняет цель с запасом (96.7–98.9 % против 90 %),
но резерв есть лишь 16–37 % времени: **две трети времени связь висит на единственном маршруте**,
и отказ одного аппарата её рвёт. Формально цель достигнута, фактически устойчивости нет.

### Критические аппараты

Аппараты, чьё изъятие рвёт связь, с числом отсчётов, где это происходит:

- 01 полная: `S02` (45), `S44` (45), `S16` (44), `S29` (43), `S45` (43), `S03` (42)
- 04 ISL 2000: `S25` (48), `S26` (47), `S20` (46), `S24` (46), `S19` (45), `S27` (45)

Числа исправлены после реализации: в первом прогоне исследования перебирались только аппараты
в пределах двух переходов от клиента, из-за чего критичные аппараты дальше по маршруту не
засчитывались. Правильный набор для перебора — все спутники, достижимые от клиента;
это и делает `core.metrics.critical_satellites`, откуда и взяты значения выше.

Это закрывает пункт доп. функционала «поиск наиболее уязвимых аппаратов» и даёт конкретику для
критерия «Анализ устойчивости».

пункт — самый сильный рычаг во всём проекте.

## 4. Проектные рычаги, ранжированные по эффекту

Прогон на `04_link_range` (ISL 2000 км, цель не выполнена ни по одному пункту):

| Изменение | C65 | C70 | C72 | Цель 90 % |
|---|---|---|---|---|
| как в файле, один шлюз | 77.50 % | 62.22 % | 65.14 % | нет |
| подбор RAAN (лучшее из 10 вариантов) | 78.61 % | 71.94 % | 69.86 % | нет |
| **+ второй шлюз (69.3° с.ш., 88.2° в.д.)** | **95.83 %** | **99.86 %** | **97.08 %** | **да** |
| + второй шлюз (71.6° с.ш., 128.9° в.д.) | 82.36 % | 94.58 % | 100.00 % | нет по C65 |
| + три шлюза | 95.83 % | 99.86 % | 100.00 % | да |

Максимальный перерыв у C70 при этом падает со 178 до 2 минут. Для сравнения на `03_satellite_outages`
второй шлюз даёт 82.9 / 89.7 / 90.0 % против 79.3 / 80.8 / 82.5 %.

**Вывод: узкое место проекта — единственная точка выхода в наземную сеть, а не группировка.**
Одна дополнительная наземная станция даёт +37 п.п. там, где перебор ориентации плоскостей даёт +10
и цели не достигает, и обходится дешевле, чем доведение плоскости с 16 до 22 аппаратов.

Оговорка для отчёта: состав наземных пунктов не входит в список параметров, которые ТЗ разрешает
менять через интерфейс (там очередь запуска, ориентация и фазирование плоскостей, периоды отказов).
Но формат `cosmo-A-1.0` допускает несколько шлюзов, а ТЗ требует строить маршрут «до доступного
шлюза» — значит сервис обязан это поддерживать, и как проектная рекомендация вывод правомерен.
Координаты выше — иллюстративные точки, как и синтетический шлюз в исходном наборе.

## 5. Динамика связей

- **Время жизни межспутниковой связи:** медиана 8 мин, 90-й перцентиль 14 мин, максимум 14 мин;
  за сутки 4338 окон. Связи живут единицы минут — поэтому маршрут и перестраивается на половине
  отсчётов, это свойство задачи, а не дефект алгоритма.
- **Задержка распространения** (из длины маршрута, c = 299 792 км/с): медианный маршрут 5007 км →
  16.7 мс в одну сторону, RTT 33 мс; самый длинный найденный 10 011 км → 33.4 мс, RTT 67 мс.
  Позволяет показывать не только «есть путь», но и его качество.

## 6. Аналитические соотношения

Связность кольца плоскости из `n` аппаратов на радиусе `r` при дальности `L`:

```
хорда между соседями = 2·r·sin(π/n)
кольцо связно  ⟺  2·r·sin(π/n) < L  ⟺  n > π / arcsin(L / 2r)
```

Для `r = 6921` км: при `L = 3000` достаточно `n ≥ 15`, при `L = 2000` нужно `n ≥ 22`.
В наборе `n = 16` — ровно между этими порогами, поэтому сценарий 04 и ломается целиком.
Формула даёт мгновенный ответ без перебора и просится в интерфейс подсказкой рядом с полем дальности.

## 7. Что из этого стоит реализовать

По убыванию отношения «баллы к трудозатратам»:

1. **Резерв маршрутов и критические аппараты** — один максимальный поток на отсчёт, десятки строк
   кода. Прямо закрывает критерий «Анализ устойчивости» и доп. пункт «поиск уязвимых аппаратов».
2. **Доставляемость с допуском по задержке** — один обратный проход по отсчётам, считается за
   то же время, что обычная доступность. Даёт вывод, которого не будет у других команд.
3. **Второй шлюз в сравнении вариантов** — не требует кода вообще, только поддержки нескольких
   шлюзов, которая и так нужна по ТЗ. Самый сильный вывод отчёта.
4. **Кратность покрытия** — счётчик видимых аппаратов, почти бесплатно, объясняет остальные цифры.
5. **Подсказка по формуле связности** рядом с полем дальности ISL.
6. Задержка распространения и время жизни связей — украшение, делать в последнюю очередь.
