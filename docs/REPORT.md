# Инженерный отчёт: устойчивость спутниковой группировки

Все числа этого отчёта получены прогоном расчётного ядра `backend/core/` (тем же кодом, что
сверяется с эталоном `tools/golden.py`) на предоставленных сценариях `Данные/*.json`. У каждого
раздела — команда, которой число воспроизводится: как минимум `python3 tools/golden.py` для базовой
доступности/перерывов, для остального — короткий скрипт на `core/` (приведён в тексте), потому что
резерв маршрутов, критические аппараты, доставляемость с задержкой и второй шлюз — это надстройка
сверх обязательных метрик (`docs/EXTENSIONS.md`), у которой нет отдельной эталонной таблицы в ТЗ.

## Постановка

Три клиентских пункта в приполярных широтах (`C65` — 65° с.ш., `C70` — 70° с.ш., `C72` — 72° с.ш.)
и один шлюз (`G_MUR`, 68.97° с.ш.) должны получать доступность **≥ 90 % времени по каждому
клиенту** на горизонте суток (`horizon_s = 86400` с, шаг `step_s = 120` с → 720 отсчётов, правый
конец сетки не включается). Доступность — доля отсчётов, на которых существует маршрут «клиент →
спутник(и) → шлюз» (клиентский пункт не ретранслирует), а не просто видимость спутника: это и есть
центральный тезис кейса — «видимость ≠ маршрут», ниже подтверждён числом дважды (сценарии 03 и 04).

## Сравнение конфигураций

Четыре сценария ТЗ отличаются ровно одним параметром от полной группировки — так виден эффект
именно этого изменения, а не смеси нескольких. Числа — `python3 tools/golden.py` (доступность,
видимость, максимальный перерыв); переходы — `core.metrics.compute(s, strategy="hops")["clients"][c]["hops"]`.

| Сценарий | Что изменено относительно 01 | C65 | C70 | C72 | макс. перерыв (C65/C70/C72) | переходы (медиана / максимум) |
|---|---|---|---|---|---|---|
| **01** полная группировка | база: 3 плоскости × 16 аппаратов, `launch_stage=3`, `isl_range_km=3000` | **96.67 %** | **98.75 %** | **98.89 %** | 8 / 2 / 2 мин | 2–3 / до 5 |
| **02** первая очередь | `launch_stage=1` — активна только плоскость P1 (16 из 48 аппаратов) | 27.22 % | 15.83 % | 12.64 % | 572 / 658 / 796 мин | 2–3 / — |
| **03** отказ 10 аппаратов | `failures` выводит 10 из 48 аппаратов из строя на части горизонта | 79.31 % | 80.83 % | 82.50 % | 24 / 24 / 20 мин | 2–3 / **до 17–18** |
| **04** ISL 2000 км | `isl_range_km` 3000 → 2000 км | 77.50 % | 62.22 % | 65.14 % | 94 / 178 / 4 мин | 2–3 / до 5 |

Видимость хотя бы одного спутника у 01 и 04 практически одинакова (97.78/99.86/100 % и то же самое
на 04 — ISL не влияет на контакт «пункт-спутник»), а доступность на 04 ниже на 20–35 п.п.: падает не
покрытие, а межспутниковая сеть. Геометрическая причина посчитана точно: хорда между соседями по
16-спутниковой плоскости на радиусе 6921 км равна `2·6921·sin(11.25°) ≈ 2700` км — при
`isl_range_km=3000` она держится, при `2000` — рвётся, и внутриплоскостных ISL-рёбер становится
**0 из 3456 возможных** (было 3456 из 5338 на 01). Кольцо каждой плоскости распадается целиком,
остаются только редкие межплоскостные контакты.

### Два дополнительных варианта, проверенных для этого отчёта

**Подбор ориентации плоскостей (RAAN) на сценарии 04.** UI-патч `{"planes": {"P1": {"raan_deg": 0},
"P2": {"raan_deg": 50}, "P3": {"raan_deg": 100}}}` вместо исходных `0/60/120°`:

```
$ python3 -c "
import json, sys; sys.path.insert(0,'backend')
from core import scenario, metrics
s = scenario.load_scenario(json.load(open('Данные/04_link_range.json', encoding='utf-8')))
p = scenario.patch_scenario(s, {'planes': {'P1': {'raan_deg': 0.0}, 'P2': {'raan_deg': 50.0}, 'P3': {'raan_deg': 100.0}}})
c = metrics.compute(p, strategy='hops')['clients']
print({k: round(100*v['avail_pct'],2) for k, v in c.items()})
"
{'C65': 78.61, 'C70': 71.94, 'C72': 69.86}
```

C70 растёт на почти 10 п.п. (62.22 → 71.94 %), но **90 % не достигается ни при какой проверенной
ориентации** (перебор 10 комбинаций, `docs/PARAMETERS.md`) — узкое место геометрии плоскостей, а не
их разворота: RAAN не чинит разорванное ISL-кольцо.

**Второй шлюз на сценарии 04** (69.3° с.ш., 88.2° в.д. — иллюстративная точка, состав шлюзов ТЗ не
относит к параметрам, управляемым через UI, но формат `cosmo-A-1.0` и контракт `/ws` рассчитаны на
несколько шлюзов, см. `docs/PROTOCOL.md`):

```
C65: 77.50 → 95.83 %   (+18.3 п.п.)
C70: 62.22 → 99.86 %   (+37.6 п.п.)
C72: 65.14 → 97.08 %   (+31.9 п.п.)
макс. перерыв C70: 178 → 2 мин
```

Один дополнительный наземный пункт даёт больше, чем полный перебор ориентации трёх плоскостей, и
единственный из проверенных рычагов на сценарии 04 **достигает цели 90 % по всем трём пунктам**.

## Анализ устойчивости

### Что рвёт отказ и где маршрут сохраняется обходом

Сценарий 03 выводит из строя 10 из 48 аппаратов на части горизонта. Доступность падает умеренно
(79–83 % против 96.7–98.9 % на 01), но маршруты заметно удлиняются — медиана переходов не меняется
(2–3), а **максимум растёт до 17–18** (было 4–5 на 01). Это и есть количественное подтверждение
вывода «сеть не рвётся, а деградирует в обходные пути»: там, где на 01 путь идёт напрямую через
1–2 спутника, на 03 сеть вынуждена обходить выбывшие аппараты через соседние плоскости, набирая
переходы. Максимальный перерыв при этом почти не растёт (24/24/20 мин против 8/2/2 мин на 01) —
резерв группировки достаточен, чтобы обход находился быстро, отказ не создаёт многочасовых провалов
(в отличие от геометрического разрыва на 02 и 04).

### Резерв маршрутов: на чём фактически держится доступность

Число вершинно-непересекающихся маршрутов «пункт → шлюз» (максимальный поток, теорема Менгера;
`core.metrics.disjoint_paths`) на 01 (полная группировка, цель 90 % формально выполнена):

| Пункт | нет пути | 1 путь (резерва нет) | 2 пути | 3 пути | **резерв ≥ 2** |
|---|---|---|---|---|---|
| C65 | 3.33 % | 80.14 % | 15.83 % | 0.69 % | **16.53 %** |
| C70 | 1.25 % | 68.19 % | 30.42 % | 0.14 % | **30.56 %** |
| C72 | 1.11 % | 61.67 % | 33.75 % | 3.47 % | **37.22 %** |

**Главный вывод анализа устойчивости.** Формально цель 90 % на полной группировке достигнута с
запасом, но **63–84 % времени связь держится ровно на одном маршруте** — отказ единственного
аппарата на этом маршруте не деградирует связь, а рвёт её в этот момент. Резерв ≥ 2 есть только
16.5–37.2 % времени (растёт от C65 к C72 — южные из трёх пунктов чаще видят сразу несколько
плоскостей). На сценарии 04 (ISL 2000 км) резерв рушится вместе с сетью: 3.2–11.1 % против
16.5–37.2 % на 01 — разорванная межспутниковая сеть не просто снижает доступность, она уничтожает
и без того малый запас устойчивости.

### Критические аппараты

Спутник считается критическим на отсчёте, если его исключение рвёт связь конкретного пункта с
шлюзом (по теореме Менгера это ровно случай, когда `disjoint_paths == 1`) — `core.metrics.critical_satellites`,
подсчитано по всем клиентам и всем 720 отсчётам:

```
$ python3 -c "
import json, sys; sys.path.insert(0,'backend')
from core import scenario, metrics
s = scenario.load_scenario(json.load(open('Данные/01_full_constellation.json', encoding='utf-8')))
for row in metrics.critical_satellites(s)[:6]: print(row)
"
{'satellite_id': 'S02', 'count': 45}
{'satellite_id': 'S44', 'count': 45}
{'satellite_id': 'S16', 'count': 44}
{'satellite_id': 'S29', 'count': 43}
{'satellite_id': 'S45', 'count': 43}
{'satellite_id': 'S03', 'count': 42}
```

На полной группировке (01) самые уязвимые аппараты — `S02`/`S16` (края плоскости P1, ближе к
пунктам) и `S44`/`S45` (плоскость P3): 42–45 отсчётов из 720, где их потеря немедленно рвёт связь
конкретному пункту. На сценарии 04 (ISL 2000 км) критичность выше и сконцентрированнее — `S25`
(48 отсчётов), `S26` (47), `S20`/`S24` (46), `S19`/`S27` (45): разорванная сеть оставляет меньше
альтернатив, и одни и те же несколько аппаратов плоскости P2 держат на себе непропорционально
большую долю связности. Практический вывод: приоритет резервирования (запасной аппарат на орбите
или ускоренный ремонт) — плоскость P2 на деградированной ISL-топологии, крайние слоты плоскостей на
полной группировке.

### Кратность покрытия — почему резерва мало даже на полной группировке

Число одновременно видимых активных спутников (`core.metrics.coverage_multiplicity`, 01):

| Узел | 0 спутников | 1 | 2 | 3 | 4+ | среднее |
|---|---|---|---|---|---|---|
| C65 | 2.22 % | 68.47 % | 27.92 % | 1.39 % | — | 1.28 |
| C70 | 0.14 % | 38.75 % | 52.64 % | 8.47 % | — | 1.69 |
| C72 | — | 27.08 % | 46.81 % | 22.78 % | 3.33 % | 2.02 |
| **G_MUR (шлюз)** | 1.11 % | **47.64 %** | 43.19 % | 8.06 % | — | 1.58 |

Резерв маршрутов упирается не в межспутниковую сеть (она избыточна), а в наземный сегмент: почти
половину времени шлюз видит ровно один спутник, и любой второй маршрут клиента обязан пройти через
тот же самый аппарат — отсюда и низкий процент резерва ≥ 2 в таблице выше даже при исправной сети.
Это прямое объяснение того, почему второй шлюз (раздел «Сравнение конфигураций») даёт больше, чем
перебор геометрии плоскостей: он снимает именно это, наземное, ограничение.

### Способы повышения устойчивости — ранжированы по проверенному эффекту

1. **Второй шлюз** — единственный проверенный рычаг, закрывающий цель 90 % на деградированной ISL-сети
   (раздел «Сравнение конфигураций»): +18…+38 п.п. на сценарии 04.
2. **Равномерное распределение очереди запуска по плоскостям**, а не по номеру аппарата (раздел
   «Рекомендация» ниже) — не поднимает итоговую доступность заметно, но на порядок снижает
   максимальный перерыв на неполной группировке.
3. **Резервирование аппаратов P2 на деградированной ISL-топологии и крайних слотов плоскостей на
   полной группировке** (раздел «Критические аппараты») — снижает вероятность одномоментного разрыва
   от единичного отказа там, где резерв маршрутов уже мал.
4. **Допуск по задержке доставки** (раздел «Рекомендация») — не требует изменений группировки вообще,
   но решает не каждый случай: спасает сценарии 03/04 (разрыв сети), не спасает 02 (нет покрытия).

## Рекомендация

**Базовая конфигурация — полная группировка (`launch_stage=3`, `isl_range_km=3000`, RAAN
`0/60/120°` как в `01_full_constellation.json`) — единственная из четырёх сценариев ТЗ, достигающая
цели 90 % по всем трём пунктам «в моменте»** (96.67/98.75/98.89 %). Условие достижения — оба
геометрических параметра одновременно: снижение `isl_range_km` до 2000 км роняет доступность на
20–35 п.п. при неизменной видимости (сценарий 04), а неполный `launch_stage` — на 60–85 п.п.
(сценарий 02), несмотря на то что оба формально «проходят» валидацию сценария.

**Если первая очередь неизбежна (запуск неполный), распределяйте её по всем плоскостям, а не по
одной.** Проверено на модификации 02 с сохранением всех остальных параметров сценария (номер
партии `launch_batch` переприсвоен по кругу — S01→батч 1, S02→батч 2, S03→батч 3, S04→батч 1, …,
вместо «первые 16 по номеру» — по 5–6 аппаратов от каждой плоскости в батче):

```
$ python3 -c "
import json, sys; sys.path.insert(0,'backend')
from core import scenario, metrics
s = scenario.load_scenario(json.load(open('Данные/01_full_constellation.json', encoding='utf-8')))
for i, sat in enumerate(s['design']['satellites']): sat['launch_batch'] = (i % 3) + 1
p = scenario.patch_scenario(s, {'launch_stage': 1})
c = metrics.compute(p, strategy='hops')['clients']
for k, v in c.items(): print(k, round(100*v['avail_pct'],2), '%', round(v['max_gap_s']/60,1), 'мин')
"
C65 28.19 %  32.0 мин
C70 22.08 %  22.0 мин
C72 12.78 %  94.0 мин
```

против исходного распределения (вся первая очередь — плоскость P1): **27.22/15.83/12.64 %, но
перерывы 572/658/796 мин.** Доступность почти не меняется (в пределах ±5 п.п., иногда даже растёт),
а **максимальный перерыв падает в 6–17 раз** (572→32, 658→22, 796→94 минут). Ограничение честно:
90 % на первой очереди недостижимы при любом распределении — 16 из 48 аппаратов физически не
обеспечивают нужной плотности покрытия; вывод про распределение — о предсказуемости и качестве
сервиса на переходный период, не о достижении цели. Ограничение реализации: сегодняшний `patch_scenario`
(и, соответственно, форма UI, DoD п.1) меняет `launch_stage` и RAAN/фазу плоскости, но не
переприсваивает `launch_batch` отдельным аппаратам — эта правка доступна через экспорт сценария,
редактирование `design.satellites[].launch_batch` и повторную загрузку (`scenario.load`), а не через
патч-форму; для эксплуатационного применения рекомендации стоит расширить `scenario.patch`, если
время проекта это позволит.

**Условия, при которых можно рассчитывать на 90 % без второго шлюза:** только полная группировка
(`launch_stage=3`) и `isl_range_km ≥ 3000` км (граница связности кольца — `n > π / arcsin(L / 2·6921)`,
для 16 аппаратов в плоскости при 2000 км нужно **не менее 22 аппаратов на плоскость**, чтобы кольцо
держалось само по себе, — альтернатива второму шлюзу, но дороже: 6 дополнительных аппаратов на
плоскость против одной наземной станции).

**Если группировка деградирована (отказы или укороченный ISL), а не в реальном времени** —
допуск по задержке доставки 10 минут (`core.delivery.delivery`, надстройка `docs/EXTENSIONS.md §1`)
выводит сценарий 04 на цель по всем трём пунктам и почти выводит сценарий 03:

| Сценарий | пункт | сейчас (T=0) | ≤10 мин |
|---|---|---|---|
| 04 ISL 2000 | C65 | 77.50 % | **90.42 %** |
| | C70 | 62.22 % | **95.00 %** |
| | C72 | 65.14 % | **96.53 %** |
| 03 отказы | C70 | 80.83 % | **89.58 %** |
| | C72 | 82.50 % | **92.50 %** |

Но это **разные диагнозы, не взаимозаменяемые исправления**: сценарий 02 (первая очередь) не
спасает никакой допуск по задержке (максимум 21.4–37.2 % даже при часе ожидания) — там пункт часто
вообще не видит ни одного спутника, проблема в покрытии, а задержка помогает только там, где путь
физически появится позже в пределах горизонта. Плюс это расширение сверх обязательных метрик ТЗ
(прямо разрешено постановкой задачи как отдельный функционал) и требует буферизации данных на борту
спутника, чего геометрическая модель этого сервиса не считает (см. «Ограничения модели» ниже) —
рекомендация ограничена случаями, где заказчик подтверждает допустимость такой задержки.

## Ограничения модели

- **Круговые орбиты, сферическая Земля** — ровно то, что задаёт `geometry.py` (не модифицируется).
  Реальные возмущения орбиты (J2, атмосферное торможение) не учитываются; на горизонте в одни сутки
  для LEO это стандартное и оправданное упрощение, но делает результат неприменимым для многолетнего
  прогноза деградации орбиты без пересчёта.
- **Только геометрия видимости и связности**, без модели радиоканала: не считаются пропускная
  способность, задержки очередей передачи, помехи, затенение антенны корпусом аппарата. Доступность
  здесь — «путь физически существует», а не «данные конкретного объёма гарантированно проходят».
  Ослабление этого допущения — расширение «доставляемость с допуском по задержке» выше, но даже оно
  не моделирует пропускную способность канала, только структуру контактов во времени.
- **Круговой угол места как единственный критерий контакта.** Реальные факторы (затенение рельефом,
  многолучевость, погода) не учитываются — `min_elevation_deg` в данных (10°) уже заложен с запасом
  под часть этих эффектов, но отчёт не может подтвердить этот запас числом без модели канала.
  Снижение порога «для улучшения показателя» напрямую запрещено методологией сравнения (см.
  `docs/PARAMETERS.md`: 5° против 10° — это 100 % против 96.7 %, число перестаёт быть сопоставимым).
- **Состав наземных пунктов — не управляемый через UI параметр.** ТЗ (DoD п.1) отдаёт пользователю
  очередь запуска, RAAN/фазу плоскостей и периоды недоступности аппаратов; количество и координаты
  шлюзов/клиентских пунктов заданы сценарием. Вывод про второй шлюз — проектная рекомендация по
  составу наземного сегмента для следующей итерации данных, а не то, что можно включить в текущем
  интерфейсе без нового сценария.
- **Отказы аппаратов и шлюзов — заданные интервалы, не случайный процесс.** Сервис не оценивает
  вероятность отказа и не строит распределение доступности по случайным сценариям отказов — только
  детерминированный расчёт для заданного набора `failures`/`gateway_outages`. Статистическая оценка
  надёжности (MTBF, Monte-Carlo по отказам) — за рамками этого расчётного ядра.
- **Одна стратегия маршрутизации в выгрузке за раз** (`hops` или `distance`, выбирается явно) —
  доступность и максимальный перерыв от неё не зависят (это достижимость в графе, `docs/PARAMETERS.md
  §5`), но конкретный `path` в выгрузке `cosmo-A-result-1.0` — зависит, и сравнивать перерывы двух
  вариантов, посчитанных разными стратегиями, для длины/переходов маршрута нельзя, только для
  доступности.
